A second opinion.
Before someone depends on the code.

Writing software is getting faster. Deciding whether it is ready still takes care. SENTINEL is my attempt to help the person making that decision: find a case where the code breaks, make it easy to reproduce, and leave the final judgment with them.

The code is written. The tests pass. But the reviewer has to think about the unexpected input, the colleague who will reuse the function, and the customer who will depend on it. I wanted another way to ask: what have we overlooked?

A tiny mistake makes the problem visible

To explore that idea, I used a deliberately broken function that turns durations into seconds. Give it 1h, and it returns 3,600. That looks right. Give it 2h, and it returns −3,600.

Two hours become a negative amount of time.

This was a planted defect in a small example, not an incident in a customer system. I chose it because you do not need to read Python to see why it matters. One reassuring example can pass while a nearby case fails badly.

Think about where a duration might travel: into a billing calculation, a scheduling rule, or an expiry setting. Whether a negative value becomes expensive, disruptive, or harmless depends on the system around it. The person reviewing the change needs to know the failure exists before making that decision.

The objective is to make review easier

SENTINEL takes a Python function and tries to find inputs that contradict its stated or inferred expectations. When it finds a failure, it checks that it happens again and tries to reduce the input to a smaller example.

For the reviewer, the useful output is a case they can reproduce. They can run it, read the intended behavior, and decide whether the code needs to change.

The distinction matters because the checker can misunderstand the contract too. A function may reject an unusual input for a perfectly good reason. A comment may be incomplete. An apparent bug may actually be a missing statement about what callers are allowed to supply.

I built the reporting around that uncertainty. Some findings describe an observed crash or hang. Others say, in effect, “this behavior conflicts with an assumption I inferred.” Those should invite a conversation with the owner of the code.

The key objective is to reduce the work between something might be wrong and here is the decision we need to make.

Where I would use it

The current project works on small Python functions. That makes it most useful where the behavior is fairly contained and a failure can be examined on its own.

  • ↗Before accepting a code change. Give a reviewer another way to challenge a parser, a calculation, or a data-transformation helper alongside the existing tests.
  • ⌕When inheriting unfamiliar code. Explore the edges of a utility before another team starts depending on it. A surprising result can reveal an assumption that was never written down.
  • ◎When reviewing code written by an agent. Ask for independent checks rather than relying entirely on the tests supplied with the change.
  • ↺After fixing a defect. Turn the reproducing example into a regression test, so the next person does not have to rediscover the same mistake.

These are places I would try it, not claims of production adoption. It is not a complete application tester, and it cannot decide whether a business rule is the right rule. Someone still has to supply that meaning.

Its approach is reusable beyond this tool: ask a separate checker to challenge a change, keep the failure small, and make the evidence available to the person who owns acceptance. That pattern could fit into a review process or a future agent workflow even if the checking engine changes.

What the experiment taught me

I tested SENTINEL by making small changes to five example functions, then asking whether it could detect the changed behavior. In the main experiment it caught 32 of 39 changes. Seven went undetected.

That was encouraging, but the comparison with generated tests stopped me from drawing a bigger conclusion. On the two clean reference functions where the comparison was valid, the generated test suite and SENTINEL caught exactly the same number: 11 of 13.

So I cannot claim this approach is generally better than asking a model to write tests. What I can say is that it offers another way to look for failures and gives the reviewer a different kind of evidence.

The findings on unchanged code were also instructive. Some exposed the defects I had planted. Others involved malformed inputs whose intended treatment was unclear. That brought me back to the same question: who decides what the function owes its caller?

A checker can expose the question. The developer or domain owner has to answer it.

See the experiment and its limitations

The archived main campaign caught 32/39 changes across five small functions. Three search seeds produced the same score. A separate set of changes to those same functions scored 35/42; this does not establish performance on unfamiliar repositories.

The successful generated-test comparison tied at 11/13 on the two clean references. Its test suites failed on the three already-buggy originals, so those cases do not support a fair head-to-head score. Ten findings on original code included seeded defects and ambiguous malformed inputs; they do not justify a zero-false-positive claim.

The current repository’s 65 tests pass locally. The historical experiments have not been rerun for this article. Targets execute in subprocesses with timeouts and resource limits; that is not a filesystem or network security boundary for hostile code.

The value is in the handoff

Finding a bug is only part of the work. Somebody has to understand it, decide how serious it is, agree on the intended behavior, and make a change without breaking something else.

A short reproducer helps that handoff. It gives the author and reviewer something shared to discuss. It can become a regression test. It lets the next maintainer see why a boundary matters.

That is the value I am trying to create with SENTINEL: less guesswork for the person who has to say yes to a change.

In Agora, I explored how to reward agents for shipping code. SENTINEL sits on the other side of that exchange. Before treating a change as progress, I want a reasonable way to challenge it.

As code becomes cheaper to produce, that responsibility stays with us. My ambition is to give the reviewer better help carrying it.

Search seeds 7, 1007, and 2007 each caught 32/39. A separate set of 42 changes to the same functions produced 35 catches. These results describe this small experiment; they do not establish how the tool performs across other repositories.

Ten findings also appeared on unchanged code: eight uncertain interval-input cases, the planted duration defect, and one observed slugify exception. A reviewer still needs to decide which inputs the function is supposed to accept.
